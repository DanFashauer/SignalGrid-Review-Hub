# SignalGrid — Evidence toolchain

You route evidence tools to the roles that already exist. Do not create a new department because a useful repository exists.

This skill supplements `signalgrid-master`. Ratified decision records, `AGENTS.md`, `CLAUDE.md`, the launch profile, and the open-source lab registry still outrank it.

## The boundary

These tools verify different layers. Keep the layers separate:

```text
source system / device
        ↓
source adapter or collector
        ↓
normalized SignalGrid evidence
        ↓
SignalGrid deterministic decision

OpenAPI + Bruno       = curated contract / wire proof
Schemathesis          = generated adversarial API proof
oasdiff               = API compatibility / breaking-change proof
Prism                 = spec-driven mock / validation proxy
Hurl                  = small deterministic HTTP regression proof
MCP Inspector         = MCP protocol/tool-surface proof
MCP Registry          = MCP metadata/discovery standard
Fleet MCP             = least-privilege MCP design reference
Mac evidence sources  = independent facts and cross-checks
```

None of these tools decides trust. None widens launch scope by existing.

## API proof stack

### Bruno — curated executable contract

Bruno remains the human-readable, Git-native API contract and wire-test plane.

Use it for named workflows, auth/tenant cases, stable negative tests, and reproductions worth reviewing in a PR.

Do not replace Bruno with generated fuzzing. A generated failure becomes a Bruno or code regression only when it represents a real product invariant worth pinning.

### Schemathesis — adversarial OpenAPI generation

Use Schemathesis when the running API and OpenAPI contract exist and generated valid/invalid inputs can discover cases the hand-written collection missed.

Required discipline:

- keep runs bounded and reproducible enough to investigate;
- preserve the failing input/seed when a real defect is found;
- distinguish schema rejection from SignalGrid policy rejection;
- do not call a run useful if zero operations or zero cases executed;
- do not let generated traffic reach a real tenant or destructive endpoint.

### oasdiff — compatibility gate

Use oasdiff on base-versus-head OpenAPI changes before release or client-impacting merges.

A breaking change is not automatically forbidden, but it must be deliberate, versioned/deprecated as required, and visible to the API contract architect and release engineer.

Do not suppress a real breaking change merely because the implementation and collection were edited together.

### Prism — spec-driven mock and validation proxy

Use Prism when a client or integration needs a truthful mock before the implementation is complete, or when validating that live HTTP traffic conforms to the published contract.

Mock success is not live-wire proof.

### Hurl — small HTTP regression surface

Use Hurl for compact shell-friendly API checks where bringing the full Bruno workflow adds no value. Do not create a second canonical API suite in Hurl; Bruno remains the curated collection.

## MCP proof stack

### Official MCP Inspector

Use the official Inspector as the independent protocol/tool-surface checker for SignalGrid MCP servers.

For a server change, verify at minimum:

- server starts without writing protocol noise to stdout;
- tools/resources enumerate;
- expected tools can be called;
- annotations match actual read/write/destructive behavior;
- structured errors remain structured;
- pagination/filtering does not silently drop or duplicate records;
- non-macOS or unavailable-probe degradation remains explicit rather than crashing.

The repository's own MCP tests stay first-party regression coverage. Inspector is an independent conformance layer, not a replacement.

### MCP Registry

Treat the registry schema/API as the external metadata/discovery standard for future publication readiness.

Do not publish a SignalGrid MCP server merely because metadata validates. Publication is an outward action and follows the owner's external-send boundary.

### Fleet MCP as a design reference

Study Fleet's MCP implementation for two patterns only unless a later decision expands the scope:

1. every MCP tool should make its required underlying API permissions visible;
2. a tool that can consume or mutate endpoint resources is not magically read-only because it is exposed through MCP.

Do not copy Fleet MCP code into SignalGrid without path-level licence review. Prefer the design lesson and an independent implementation.

## macOS / endpoint evidence stack

The first-party `signalgrid-mcp` server remains the Mac-native `grid_collected` path. Independent projects are used to challenge or enrich the evidence model, not to overrule provenance.

### Fleet + osquery

Use Fleet/osquery as the managed endpoint source and as a source-independence comparison against native Mac reads. A fact from Fleet carries Fleet/osquery provenance; a fact from `signalgrid-mcp` carries grid-collected provenance. Do not collapse them because the values match.

### MacAdmins osquery extension

Use `macadmins/osquery-extension` as a high-value reference/cross-check for Mac-specific tables such as MDM state, software-management state, SOFA-derived update/security state, Unified Log and network quality.

Before adopting any table into a SignalGrid proof:

- capture what the extension actually emits;
- map it to an existing evidence dimension where possible;
- record source timestamp/freshness and required privilege;
- compare it against the first-party collector or Fleet where overlap exists;
- keep disagreement as contradiction evidence, not as a reason to pick the friendlier source.

### SOFA

Treat SOFA as independent Apple software/security currency data. It is valuable specifically because it answers a different question from MDM: whether the observed OS/security-data state is current against Apple's published release/security cadence.

DR-001's breadth freeze still controls productization. Researching or consuming SOFA in a lab does not create a new launch connector.

### Munki

Use Munki as a software-management reference/lab source when validating installation state, managed software intent, and update workflow behavior. Do not equate Munki desired state with installed/healthy state without observation.

### Santa

Use Santa as future endpoint-security/execution evidence research. Keep it deferred unless a current SignalGrid dimension explicitly needs execution authorization/event evidence and the launch scope permits the work.

### ReportMate

Study ReportMate primarily as a reference for combining Mac/osquery collection, API exposure and MCP. Treat its server/API/MCP licensing as a separate review before any reuse. Do not embed AGPL/server code into the MIT Review Hub by convenience.

## Review stack — Ponytail (owner-directed, DR-024)

Ponytail (`@dietrichgebert/ponytail` v4.9.0, MIT, pinned to commit `2ed6c52`, vetted 2026-09-01) is the **top lens of the review stack** under DR-024. It is a **minimalism lens** — a seven-rung ladder applied before code is written (does it need to exist → is it already in this codebase → stdlib → native platform → installed dependency → one line → only then the minimum). It ranks and licenses removal; the other lenses judge whether what remains is right.

- **Install:** `pnpm run ponytail:install` (`scripts/install-ponytail.mjs`) — clones to `$PONYTAIL_DIR` (default `~/dietrichgebert/ponytail`), checks out the **pinned commit `2ed6c52`**, `claude plugin validate`s it, registers that LOCAL CLONE as the marketplace, installs `ponytail@ponytail` at **user scope** non-interactively, and sets default mode `ultra`. The pin is the point: `/plugin marketplace add DietrichGebert/ponytail` tracks the author's moving HEAD, which this repository does not permit. Every step exits 1 on failure.
- **Hooks ON, unlike ECC's.** Read 2026-09-01: three small Node scripts that only inject the ruleset text and record the mode under `~/.config/ponytail` — no child process, no network, no secret reads. ECC's hooks *run passes*; Ponytail's only speak. That difference is the whole reason one set is installed and the other is not.
- **What it never cuts.** Trust-boundary validation, error handling that prevents data loss, security, accessibility, anything explicitly requested, and one runnable check per non-trivial logic. Its never-cut list protects exactly what the fail-closed doctrine protects, which is why "Ponytail on top" does not fight this repository's gates — the first audit left every proof, guard and `default:` arm in place.
- **What it is NOT.** By its own charter it is **not** a correctness, security, or performance reviewer, and it certifies nothing green. A Ponytail-clean diff is a diff with nothing surplus in it, not a diff that works. Correctness routes to a normal review pass (ECC, then this repository's own sweeps); `preflight` + `verify:breadth` are still the only things that say green.
- **Skills:** `ponytail` (the ladder), `-review` (per diff), `-audit` (ranked cut list), `-debt` (deliberate-shortcut ledger), `-gain`, `-help`. The audit's cut list is **executed**, not merely noted — bounded by the never-cut rules above and by this repository's gates.
- **Evidence:** `docs/agent/PONYTAIL_AUDIT_2026-09-01.md` (first scan, three parallel auditors, `ultra`), `docs/DECISION_RECORDS.md` DR-024, `docs/agent/RESOURCE_INTAKE.md` (row 2026-09-01).

## Web research and source verification — Firecrawl (owner-directed, DR-022)

Firecrawl (web → LLM-ready markdown) is the **research / source-verification** lane, adopted on top of ECC by owner direction (DR-022). It answers "what does this external page actually say" — competitive intel, verifying an outside claim, reading a vendor doc — the same job a human browser does, faster.

- **Install:** `FIRECRAWL_API_KEY=fc-... pnpm run firecrawl:install` — registers the **MIT** `firecrawl-mcp@3.24.0` hosted-API client as a user-scoped MCP server for Claude Code. It fails CLOSED without a key and never writes the key into the repo. It is the disciplined inverse of the vendor one-liner (`npx -y firecrawl-cli@latest init --all --browser`): pinned, single-client, key-gated.
- **Licence:** use the hosted API through the **MIT** client. Do **not** self-host or vendor the `firecrawl/firecrawl` **server** (AGPL-3.0) — that is the copyleft surface INTAKE_LEDGER row 97 flagged, and it stays out.
- **Layer:** report-only research. Firecrawl output is external web content and is **never** an authoritative verdict — the cross-source contradiction rule and "do not use an MCP result as a verdict unless the deterministic core computed it" both apply. It never enters a decision path, a proof fixture, a connector, or the product build.
- **When NOT to reach for it:** if a plain fetch or an already-connected source answers the question, use that — row 97's redundancy point still holds for the common case. Firecrawl earns its use on pages that resist a plain fetch (JS-rendered, crawl-shaped, multi-page).

## Operating memory — Neural Memory (owner-directed, DR-026)

Neural Memory (`neural-memory` v4.62.0, MIT, pinned to commit `2015cb9b`) is the **memory substrate** under the DR-024 stack: a Python MCP server (`nmem-mcp`) over a local SQLite graph that lets a session remember what an earlier one learned about working this repo. It sits under every lens and is not one of them.

- **Install:** `NEURALMEMORY_DIR=/path/outside/the/repo pnpm run neural-memory:install` — `uv tool install` pinned to the commit (no PyPI fallback), then `claude mcp add --scope user`. It fails CLOSED: no `uv`, no `claude`, an in-tree store path, a failed install, a missing `nmem-mcp`, or a failed registration each exit 1. It never installs the plugin form or any hook.
- **Layer:** substrate. It judges nothing, it is **never** a verdict source ("do not use an MCP result as a verdict unless the deterministic core computed it" applies in full), and nothing in `lib/*`, `artifacts/api-server`, or a proof may import, call, or read it.
- **The store rule:** `NEURALMEMORY_DIR` lives OUTSIDE the repo; `.neuralmemory/` is gitignored because the tool's surface writer targets any `.git`/`package.json` root. A store inside a checkout is refused by the installer, not merely discouraged.
- **Hooks OFF, and why:** the plugin form ships four Claude Code hooks — two ingest the session transcript, one logs every tool call — behind a PyPI-latest server. Memory here is written by a deliberate tool call or not at all, the same call made for ECC. The one-time `config.toml` also turns off the PyPI version check, Mem0, sync and Telegram.
- **Session start:** call `nmem_recap` **in addition to** the `docs/agent/LOOP.md` ritual (read LOOP.md, run `pnpm run loop:state`), never instead of it. Committed docs are the memory of record; the store is a cache of them.
- **What it never holds:** tenant data, secrets, PHI, `artifacts/live-evidence/`, or an index of the tree — operating memory only (a gate's quirk, a lane's state, an owner preference).

## Adoption gate for every new source or tool

Before a candidate becomes installed/deployed/required:

1. Check `docs/OPEN_SOURCE_LAB_REGISTRY.md` and its JSON twin.
2. Record classification, tier, accountable role, exact licence basis, credential class, mutation rights and deployment evidence.
3. Default mutation rights to false.
4. Separate `study`, `run as separate service`, `call its API`, `vendor`, and `embed`; they are different licence/security decisions.
5. Pin versions or provenance where the tool enters CI/release evidence.
6. Add a negative/self-test for any new gate.
7. Prove the invocation is non-vacuous — expected operations/cases/tools actually ran.
8. Keep secrets and real tenant/customer data out of the public Review Hub.
9. Do not change launch classifications without a new decision record.

A candidate may be referenced in research before registry intake, but it may not be called deployed, required, or product surface until the registry and applicable decision gates say so.

## Cross-source contradiction rule

When two sources disagree, SignalGrid does not choose the source that produces the least friction.

Record:

- both source identities;
- both observation times;
- collection method/fidelity;
- the conflicting fields;
- freshness of each;
- whether either source is authoritative for that fact;
- the policy consequence of unresolved disagreement.

A contradiction tightens assurance at least as hard as an absence unless a ratified policy explicitly resolves that evidence class differently.

## What not to do

- Do not add all of these tools to CI at once.
- Do not create a connector because a repository has an API.
- Do not turn the Mac lab into a second product roadmap.
- Do not use an MCP client or server result as an authoritative verdict unless the deterministic SignalGrid core computed it.
- Do not call a mock, fixture, generated test or local lab run customer proof.
- Do not copy code because a public repository appears permissively licensed; verify the exact path and distribution model.
- Do not replace one proof layer with another merely to reduce the number of red checks.

## Completion

A toolchain change is complete only when the responsible role is named, the tool's proof layer is explicit, scope has not widened, licence/security posture is recorded, the run can fail meaningfully, and the resulting evidence is reproducible by another agent.
