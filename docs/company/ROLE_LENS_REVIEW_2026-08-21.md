## Product

**Verdict:** The engineering core and the scope machinery are genuinely strong — the launch profile, the GA route allowlist, and the console's preview banner are the best-built scope discipline I have reviewed in this repo — but the product's actual customer-facing contract is thinner than its governance: the verdict vocabulary a host app must render is undocumented and partly fictional, the published API contract advertises twenty routes a commercial deployment refuses, and two of the three docs that claim to define what SignalGrid is were written before DR-005 froze it and have never been reconciled to it.


### product.1 [SERIOUS] The worker-facing reason-code table names four codes the engine cannot emit — and no reason-code catalog exists anywhere

*Citation:* docs/ECOSYSTEM_FLOW_AND_RESOLUTION.md:107-113 (§2.1 table) and :130-136 (§2.2 resolution table); lib/api-spec/v1-openapi.yaml:1047-1049 (reasonCodes: items {type: string} — no enum)

Under the embedded-UX law the verdict plus its reason codes ARE the product surface: the host app renders the worker's message from them. §2.1 is the only doc mapping codes to worker language, and 4 of its 7 codes — DEVICE_POSTURE_STALE, IDENTITY_UNVERIFIED, WRONG_BAY_OR_CUSTODY, CRITICAL_ON_UNTRUSTED_DEVICE — return zero hits across all .ts/.tsx/.swift in the tree (real codes are POSTURE_STALE and CRITICAL_WORKFLOW_UNTRUSTED_DEVICE). lib/signalgrid-core/src emits ~40 distinct codes; lib/signalgrid-core/src/resolution.ts, which implements §2.2's Resolution Assistant, shares none of §2.2's vocabulary (it emits only BATTERY_CRITICAL/BATTERY_FAILING). A design partner's host-app developer implementing this map would ship messages that never fire, and the published contract gives them an untyped string array instead. This is the Shared-Device Trust PM's first named output (reason-code specification) and its KPI (every reason code maps to one host-app message pattern and one fixture) — it does not exist.

## Product design & research

**Verdict:** The design system is genuinely well-reasoned where it is written down and genuinely unenforced where it is rendered: DR-005's ratified decision palette reached two of six token trees, no web surface consumes the decision tokens at all, and with roughly a hundred `proof:*` gates in this repo not one of them watches a color — so the single doctrine this company runs on, that every claim needs an executable counterexample, has never been applied to the surface where a wrong answer is communicated to a human.


### design.1 [BLOCKING] DR-005's deny re-tone reached 2 of 6 rendered token trees — three shipped web apps and SignalGridMobile still carry pre-DR-005 decision colors

*Citation:* artifacts/signalgrid-review/src/index.css:128 (`--decision-deny: 0 28% 49%` = #A05A5A); artifacts/signalgrid-desktop/src/index.css:84 (same); artifacts/signalgrid-mobile-pwa/src/index.css:85 and :136 (same); native/ios/SignalGridMobile/SignalGridOperator/Theme.swift:12-15 (sgAllow #6FA88C, sgStepUp #C29A66, sgRestrict #C99B6B, sgDeny #C07474 — a fourth, undeclared palette); vs canonical artifacts/signalgrid-web/src/index.css:97 and native/ios/EnterpriseShell/Services/DesignSystem.swift:68-70 (#C67070)

My KPI is literally 'zero token forks between trees at merge' and 'every design change ships to all rendered surfaces in one commit'. DR-005 commit 87e1735 touched DesignSystem.swift and two index.css files; `git log` on Theme.swift shows its only commit is 4a170db (a status restamp), and the three stale web trees were never touched. The value still sitting in them, HSL(0,28%,49%), is exactly the #A15B5B that docs/BRAND_CONTRAST_FINDING.md records as replaced for measuring 3.18:1 on card — the weakest contrast in the system on the most safety-critical state. It is still shipping. Worse, docs/APP_SUITE_MATRIX.md:38 names `signalgrid-review` as the Operator Console, which is precisely the surface BRAND_CONTRAST_FINDING warned about: 'a deny rendered as one red in the review console and a different red on the device is a worse defect than any contrast ratio.' That defect now exists. Separately, Theme.swift maps `restrict` to its own amber #C99B6B while both canonical trees map restrict→deny red (DesignSystem.swift:118) — the same verdict is a caution on one SignalGrid surface and a hard stop on another, which is a change to what a verdict color means, something my role cannot approve alone and nobody approved at all.


### design.2 [BLOCKING] The `--decision-*` tokens are consumed by no rendered surface; every web app paints verdicts from raw Tailwind ramp colors, and they disagree with each other and with themselves

*Citation:* artifacts/signalgrid-review/src/components/sections/SignalGridSimulatorSection.tsx:24-25 (`restrict` and `deny` are byte-identical class strings); OperatorConsoleSection.tsx:65-66 (restrict=red-300, deny=red-200); CredentialReaderDashboardSection.tsx:11 (restrict=amber); WorkerSelfServiceSection.tsx:60 (restrict=orange-300); connector-emulator/ConnectorEmulatorDashboard.tsx:10-11 (restrict=amber); artifacts/signalgrid-app/src/components/LiveDecisionPanel.tsx:23-26 (allow=emerald-400) vs artifacts/signalgrid-app/src/index.css:178-185 (allow=green-500, used by StatusBadge.tsx:7)

Owning the decision-state palette as a safety surface means one object behaves the same everywhere, and today it does not behave the same twice.


### design.3 [SERIOUS] White is hardcoded on an `SG.allow` fill at 3.72:1 — the exact defect `SG.onDeny` was created to fix, with no `onAllow`/`onReview` counterpart

*Citation:* native/ios/EnterpriseShell/Views/ActiveSessionViewController.swift:821-825 (`toast.textColor = .white; toast.backgroundColor = SG.allow`, 14pt via SG.sans(14,.medium) at line 827); token defined at native/ios/EnterpriseShell/Services/DesignSystem.swift:68 and the rule it violates written at :72-78

DesignSystem.swift:72-78 states the principle in its own words — 'Never hardcode .white on a deny fill' — because white on the re-toned dark deny measures 3.53:1, so the foreground flips instead. The same reasoning was never applied to the other two decision states, and no `SG.onAllow` or `SG.onReview` token exists. I measured white on the dark `allow` #5E8F73 at 3.72:1 and white on the dark `review` #B08B57 at 3.15:1, both under the 4.5:1 floor DR-005 ratified for decision states, on 14pt text that is not large text by any WCAG reading. This is distinct from the tracked allow-as-text 4.32:1-on-card item (in-flight task #28): that one is allow used as a foreground, this one is allow used as a ground. Fixing the token value will not fix this line. A toast is how the shell confirms an action succeeded on a shared frontline device, in a corridor, at whatever brightness the ward has.


### design.4 [SERIOUS] EnterpriseShell ships zero explicit accessibility affordances — no labels, no traits, and no VoiceOver announcement when a verdict or session state changes

*Citation:* native/ios/EnterpriseShell — `grep -rn "accessibilityLabel|isAccessibilityElement|accessibilityTraits"` returns 0 across all 37 Swift files, against 65 UILabel/UIButton constructions in Views/; the only `UIAccessibility.` references in the tree are Guided Access calls in Services/KioskController.swift:34, 44, 47, 72, 87 — no `UIAccessibility.post(notification:)` anywhere. ## Engineering

**Verdict:** The engineering estate is structurally healthier than its reputation — no dependency cycles across 35 lib packages, no undeclared workspace imports, typecheck genuinely reaching every package (I probed five out-of-reference packages with injected type errors and all five were caught), and a device seam that clamps to the stricter of local and remote — but the contracts at its edges have quietly drifted out from under their own gates: two native Assist clients and 42 conformance vectors are bound to a `/v1` envelope no route serves, the resolution planner tells a worker a DENY is self-service whenever a reason code has no descriptor, and the integrations catalog's per-item route publishes synthetic vendor connection status with the disclaimer stripped off.


### engineering.1 [SERIOUS] The Assist wire has two clients, 42 conformance vectors and a preflight gate — and no server implementation

*Citation:* native/shared/assist-wire-conformance.json (cases parse {"assist":"allow"…}); native/android/core/src/main/kotlin/com/signalgrid/assist/core/AssistWire.kt:10 ("Turning an HTTP result from `/v1` …"); native/android/core/src/main/kotlin/com/signalgrid/assist/core/GateEndpoint.kt:47 and native/desktop/core/src/endpoint.rs:22 (both append `/v1/authorize`); artifacts/api-server/src/routes/v1.ts and lib/api-spec/v1-openapi.yaml:74-633 (no `assist` response key, no `/v1/authorize` path)

I own the /v1 envelope. The Kotlin and Rust Assist clients — the two bound by the shared vectors and by scripts/check-assist-conformance.mjs in preflight — decode an envelope `{assist, reasons, decisionId}` from a route `/v1/authorize` that this repository does not implement. The one client that talks to the real server, iOS RemoteDecisionService (native/ios/EnterpriseShell/Services/DecisionService.swift:78), decodes a completely different envelope `{decision:{outcome}, plan:{outcome}}` from /v1/app-workflows/evaluate — and is outside the vector suite by the conformance gate's own disclaimer, whose stated reason ("EnterpriseShell ports the DECISION ENGINE rather than consuming /v1 as a wire client") is now false. Verified with `pnpm run check:absence "v1/authorize"` (exit 2, inconclusive) and by reading all four matches: every one is a URL-normalization comment or its test, none is a route. Net effect: a green conformance gate proves two SDKs agree with each other about a contract nothing serves, while the seam that actually ships is ungated. That is the exact 'gate that is green in both directions' class this repo names as its worst defect.


### engineering.2 [SERIOUS] The resolution plan silently drops any reason code with no descriptor, reporting a DENY as self-service and auto-resolvable

*Citation:* lib/signalgrid-core/src/resolution.ts:396-398 (`const descriptor = DESCRIPTORS[code]; if (!descriptor) continue;`) and :419 (`const autoResolvable = steps.length > 0 && !hasManual`); unmapped emitters at lib/signalgrid-core/src/policy.ts:319 (NO_RULE_MATCHED_DEFAULT_STEP_UP) and :327 (ALLOW_SUPPRESSED_DEGRADED_EVIDENCE); tenant-authored codes enter at policy.ts:310 (`reasonCodes.push(rule.reasonCode)`)

Executed counterexample against the real core (buildResolutionPlan, no mocks): a decision with reasonCodes [POSTURE_STALE, TENANT_CUSTOM_BLOCK] and outcome `deny` returns `path: "self_service"`, `autoResolvable: true`, worker text "You can resolve this yourself in a moment", and operator text "DENY · path=self_service · 1 self-service, 0 approval-gated, 0 manual". Same result for [POSTURE_STALE, ALLOW_SUPPRESSED_DEGRADED_EVIDENCE] on a `restrict` — and that second code needs no tenant customization, it is the shipped fail-closed guardrail at policy.ts:327. DESCRIPTORS covers 30 codes; the policy engine can emit codes that are not in it, and rule reason codes are tenant data, so the set is open by construction. An unknown code should raise the plan's class, not vanish from it — golden rule 2 — and the file's own comment at resolution.ts:177-181 names this self-contradictory-verdict shape as the thing the invariant exists to prevent. The zero-step case is handled (workerSummary line 499) and simulateResolution re-runs the policy so it cannot project a false allow; the mixed case is the hole, and no gate asserts DESCRIPTORS is total over the emitted vocabulary.

*Citation:* artifacts/api-server/src/routes/integrations.ts:2015-2023 (collection body carries `demo: true` + `note`) vs :2026-2039 (`res.json(integration)` — raw object, no envelope); fabricated fields at :7-58 etc.; assertions at artifacts/api-server/test/api.test.mjs:218-222 check only status codes
