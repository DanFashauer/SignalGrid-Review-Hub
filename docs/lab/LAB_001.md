# LAB 001 - the first real decision

**Goal: the grid decides something true, about real hardware, and a cascade
fires. On a MacBook Air M4 and an iPhone. Nothing purchased.**

This is the first time SignalGrid decides on a real signal instead of a fixture.
Everything before this was the engine running on invented inputs.

Lane: **MAC / LOCAL LAN.** None of this can be proven in a container - which is
the point (`docs/PURPOSE.md`, DR-020).

---

## What you own, and what each part becomes

| Layer | Hardware you have | Software (all free) |
| --- | --- | --- |
| Credential | iPhone | NFC tag read, or BLE proximity |
| Identity | - | Keycloak (Docker) |
| **Device posture** | **MacBook** | **`signalgrid-mcp` - real macOS signals** |
| Zone / location | iPhone + Mac | BLE proximity: near / away |
| Decision | MacBook | the deterministic core |
| Cascade | - | Home Assistant (Docker), virtual entities |
| Escalation | iPhone | ntfy push |

**Home Assistant virtual entities are not a cheat.** A `light.template` exists in
the UI and in the API; the `call_service` payload is byte-identical to one
driving a real bulb. For proving the *cascade*, a virtual light that visibly
turns off is worth what a real one is worth. Swap in hardware later; the code
does not change.

---

## Step 1 - real posture, replacing a fixture

**Do this first. It is the highest-value step in the whole lab**, because it is
the first true signal the core has ever seen.

```bash
cd ~/signalgrid-mcp
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest -q                      # expect 99 passed
python -m signalgrid_mcp.server # stdio; leave running
```

Then in the Review Hub, point the macOS posture connector at it instead of the
fixture, behind a flag (default off, per connector discipline — the engineering
freeze this line used to cite was lifted in full by DR-021 on 2026-08-31; the flag
stays off because `check-connector-discipline.mjs` requires every family to be
gated, which is a standing rule and not a freeze):

```
SIGNALGRID_MACOS_POSTURE=live
SIGNALGRID_MCP_CMD="python -m signalgrid_mcp.server"
```

**Done when:** a Decision Envelope carries `source: signalgrid-mcp` with your
actual FileVault / SIP / Gatekeeper / firewall state and a real `observedAt`.

**Watch for:** the MCP server's three-way classification means an unreadable
probe returns `null`, not `false`. Unknown must raise assurance, never lower it.
If a decision flips to allow because posture came back unknown, that is a
fail-closed violation and the lab stops until it is fixed.

## Step 2 - the cascade

```bash
docker run -d --name homeassistant --restart=unless-stopped \
  -e TZ=America/New_York \
  -v ~/signalgrid-lab/ha:/config \
  --network=host ghcr.io/home-assistant/home-assistant:stable
```

Open `http://localhost:8123`, create an account, then add two virtual entities
in `~/signalgrid-lab/ha/configuration.yaml`:

```yaml
light:
  - platform: template
    lights:
      ward_4_room_light:
        turn_on:  { service: input_boolean.turn_on,  target: { entity_id: input_boolean.room_light } }
        turn_off: { service: input_boolean.turn_off, target: { entity_id: input_boolean.room_light } }
        value_template: "{{ is_state('input_boolean.room_light','on') }}"

input_boolean:
  room_light:      { name: Room light }
  bedside_display: { name: Bedside display }
```

Create a long-lived access token (profile -> Security), then confirm SignalGrid
can drive it:

```bash
curl -X POST http://localhost:8123/api/services/light/turn_off \
  -H "Authorization: Bearer $HA_TOKEN" -H "Content-Type: application/json" \
  -d '{"entity_id":"light.ward_4_room_light"}'
```

**Done when:** a `restrict` or `step-up` verdict turns that light off, and the
`requested actions` / `execution results` fields of the envelope both populate.

**Boundary:** Home Assistant remains authoritative for the devices. SignalGrid
decides and asks. It never manages an entity directly.

## Step 3 - identity

```bash
docker run -d --name keycloak -p 8080:8080 \
  -e KEYCLOAK_ADMIN=admin -e KEYCLOAK_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:latest start-dev
```

One realm, one user, one group (`ward-4-clinical`). Read login events through
the admin API as the identity signal. Later this becomes the SSF/CAEP receiver
(`docs/INTEGRATION_MAP.md`) - do not build that yet.

## Step 4 - the credential and the moment

Two options, neither requiring purchase:

**BLE proximity (nothing to buy).** The Mac reads iPhone BLE RSSI; crossing a
threshold is "entered the zone." Coarse and jittery - debounce it, and treat an
unreadable reading as unknown, not absent.

**NFC tag (~$10 if you ever want one).** iPhone Shortcuts fires an NFC
automation that POSTs to your local API. Closest to a real badge tap, and the
one to use for a demo.

Either way the event is the same shape: `subject`, `zone`, `observedAt`.

---

## Step 5 - escalation

```bash
docker run -d --name ntfy -p 8090:80 binwiederhier/ntfy serve
```

Subscribe on your iPhone (free app). When verification shows the expected
outcome did not occur, publish to the topic. **This closes the loop the
doctrine requires: decide -> request -> observe -> verify -> escalate.**

---

## The demo, once all five steps run

> Phone approaches the Mac. Real macOS posture, read live. Identity from
> Keycloak. The core decides. The light goes off, the display changes, a push
> lands on the phone. Then change one input - let posture go stale - and the
> verdict recomputes to `step-up` in front of the person watching.

Nobody watching needs to know the light is virtual. **That is the whole thesis,
end to end, on hardware already owned.**

---

## Definition of done

- [ ] A Decision Envelope carries a **real** macOS posture signal, not a fixture
- [ ] Unknown posture raises assurance - verified deliberately, not assumed
- [ ] A verdict drives a Home Assistant entity; `requested actions` and
      `execution results` both populate
- [ ] `verification` records whether the expected outcome actually occurred
- [ ] A failed verification produces an ntfy push
- [ ] Counterfactual replay: change one input, verdict recomputes, same policy
      version, same rationale
- [ ] The whole run is reconstructable from the envelope afterward

## What this lab must not become

- No new connectors beyond these five.
- No industry-specific logic anywhere in the core.
- No step added for the person. If the demo requires explaining an interaction,
  the embedded UX law has been broken.
- No writes to a system of record. Home Assistant is the only actuator, and it
  is a lab.
